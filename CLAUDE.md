# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**Rhabdomancer** is a headless IDA plugin (written in Rust) that locates calls to potentially insecure API functions in binary files. It uses `idalib` ([idalib-rs](https://github.com/idalib-rs/idalib)'s Rust bindings to the IDA SDK) to auto-analyze a binary, finds the known bad API functions listed in its configuration, and marks each call site with a bookmark and a comment in the IDB, which it saves next to the binary.

## Build requirements

- IDA 9.5+ (see the README's compatibility table), with `IDADIR` set to the installation directory at both build time and runtime. The build script (`build.rs`, via `idalib-build`) checks common installation paths if it's unset, and only warns if it can't find IDA, so set it explicitly for non-standard locations (`export IDADIR=/path/to/ida`).
- LLVM/Clang, used by bindgen when building `idalib`. On Windows, `LIBCLANG_PATH` must also be set to the LLVM/Clang `bin` directory.
- Rust edition 2024, and Rust 1.88+ (declared as `rust-version` in `Cargo.toml`): the code uses `let` chains, and idalib's `cxx` dependencies require 1.88 too (checked by building with 1.86). Clippy's `incompatible_msrv` finds no API newer than 1.85, the minimum for edition 2024, so the floor comes from the language feature and the dependencies rather than from APIs.

## Commands

```bash
# Build
cargo build --release --locked     # optimized (LTO, stripped, O3)
cargo build --locked               # debug build (no debug info, for faster startup)

# Unit tests (no IDA database needed)
cargo test --lib --locked

# Integration tests (custom harness, needs a working IDA installation)
cargo test --test tests --locked

# Lint and format (CI enforces these as errors)
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings

# Documentation (CI enforces this as an error)
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked

# Dependency vulnerability audit (requires cargo-audit)
cargo audit

# Semver compatibility (requires cargo-semver-checks)
cargo semver-checks
```

`--workspace` follows the `rust-style` skill; this is a single crate, so it is equivalent to CI's `cargo clippy --all-targets --locked -- -D warnings`. `--no-deps` matches CI's `build.yml` doc step and skips documenting dependencies (`doc.yml`, which publishes to `gh-pages`, runs a plain `cargo doc --locked`).

CI's own `test` step only runs `cargo test --no-run` — a compile-only smoke check. Both test suites link against the IDA libraries, and the integration suite also needs a working IDA installation to analyze binaries, which CI runners don't have, so both only run locally.

## Architecture

This is a single crate: `src/main.rs` (CLI entry point) and `src/lib.rs` (all core logic).

- **`src/main.rs`** — CLI entry point. Prints the banner, calls `force_batch_mode()` to suppress IDA UI, parses a single binary path argument (printing usage for none, several, `-h`, or `--help`), then delegates to `lib::run()`.
- **`src/lib.rs`** — Core analysis logic. Public entry point: `run(filepath: impl AsRef<Path>) -> anyhow::Result<BookmarkIndex>`. It is the only public item: everything else, including `PREFIX` (`"[BAD "`, private since 1.0), is internal, so the public API stays minimal (making items public later is non-breaking; CI runs `cargo-semver-checks`). A library API for other crates (e.g., a `scan()` returning findings without printing) would be designed separately rather than by exporting these CLI-oriented types. The annotation text is an external contract (see Output).

### Key types and functions

- `KnownBadFunctionsConfig`: Mirrors the configuration file (`high`/`medium`/`low` name lists); only used as the deserialization source of `KnownBadFunctions`. All three lists are required, and `#[serde(deny_unknown_fields)]` rejects any other key, so a misspelled priority (e.g., `meduim`) fails loudly instead of being silently ignored.
- `KnownBadFunctions`: Loads the configuration into a single `HashMap<String, Priority>` keyed by normalized name. Deserialized via `#[serde(try_from = "KnownBadFunctionsConfig")]`: the `TryFrom` impl strips decorations from (`strip_decorations()`) and normalizes every name and rejects the configuration at the first name that is empty or is listed under multiple priorities (after normalization), so `parse()` deserializes straight into `Self` with `toml::from_str`. `load()` parses the file at `RHABDOMANCER_CONFIG` if set and not empty (an empty value counts as unset, so clearing the variable restores the built-in list) (read with `fs::read_to_string`, adding the file path as `anyhow` context to read and parse errors), or the built-in `DEFAULT_CONFIG` otherwise, printing `[*] Using built-in configuration (set RHABDOMANCER_CONFIG to use a custom one)` so the way to customize is shown on every run (with no fallback to a file on disk, so which configuration is used never depends on the source tree); the unit tests call `parse()` directly, so they exercise the same parsing path as `load()`. Duplicates are detected with `*functions.entry(name).or_insert(priority) != priority`, which keeps the first occurrence and compares against it in one expression. `lookup()` normalizes a `&str` and returns the stored normalized name (via `get_key_value`, borrowed from the map) and its priority, so callers never normalize twice; it is unit-testable without an IDB. `lookup(func_name, kind)` first strips platform decorations (`strip_decorations()`), then tries, in order, the normalized name, `strip_alias_prefix()`'s result, and `strip_ida_suffix()` applied to that (or to the normalized name), the last only for stubs (`FunctionKind::Stub`, see `is_stub()`) and library aliases; the candidates are `[Option<&str>; 3]` flattened into a `find_map`, and the two helpers return `None` when there's nothing to strip, so no candidate is looked up twice. An exact match always wins, so a configured name such as `strcpy_1` keeps its own priority, and the aliased name (`aliased`, the alias without its prefix) is tried before stripping the suffix, so a custom `foo_2` matches `__o_foo_2`.
- `BadFunctions<'a>`: Pure data: the bad functions found in the opened IDB, in a single `BTreeMap<(Priority, FunctionId), FoundFunction<'a>>` (the composite key stays a tuple, as in the rust-style skill, while the value is a named struct so that its fields, especially the kind, are self-documenting), so iteration visits high, then medium, then low priority, each ordered by function ID. In ELF binaries a bad API function usually matches twice, as its `.plt` stub (printed as `(thunk)`) and as its import, and both are kept on purpose, so their call sites are listed twice (on `tests/data/ls` all 10 functions appear as identical thunk/import pairs; `tests/data/double_xref` pins it for `system`). Don't deduplicate them: dropping the stub by name would lose its marks whenever the import's traversal doesn't reach its callers (an unrelated function that normalizes to the same name, e.g. a local `_strlen` vs `strlen@plt`, or a stub IDA doesn't link to the import). A structural check (drop the stub only if the import has an XREF from inside it) would be safe, but was rejected in favor of simplicity: the repetition is cosmetic, since the `bookmarked` set marks each call site once. ARM64X binaries give similar pairs, kept for the same reason: both the x64-compatible `X` and the native ARM64EC `#X` match (on `cmd.exe`: `swscanf`, `printf`, and `vsnwprintf`), as `X` and `_X` did on IDA 9.4, and neither is labeled `(thunk)`. `find_all()` is a single `filter_map(...).collect()` that fetches each function's name once (an FFI call plus a `String` allocation), computes the function's `FunctionKind` once (`Stub` if `is_stub()`, otherwise `Plain`), passes it to `lookup()`, and stores it in the `FoundFunction` for `mark_calls()`' `(thunk)` label (so the THUNK flag isn't fetched twice over FFI), and stores the function with the normalized name returned by `lookup()`, borrowed from `KnownBadFunctions` (hence `find_all(idb: &'a IDB, bad: &'a KnownBadFunctions, plt: &PltSegments)`, a single lifetime for both stored borrows; `plt` is only used during the call). `iter()` exposes the entries as flat `(priority, id, func, name, kind)` tuples in map order, so consumers such as `CallMarker` don't depend on the map's layout; it has no `#[must_use]` because `impl Iterator` already is (adding one triggers clippy's `double_must_use`).
- `FunctionKind`: `Plain` or `Stub`, the kind of a matched function, passed to `lookup()` (where IDA's numeric suffix is stripped only from stubs) and stored in `FoundFunction` for the `(thunk)` label. An enum rather than a `bool`, following the rust-style skill ("enums instead of flags"), so that call sites such as `lookup("strcpy_0", FunctionKind::Stub)` read on their own, unlike `lookup("strcpy_0", true)`; `is_stub()` stays a `bool` predicate, converted once in `find_all()`.
- `FoundFunction<'a>`: The value of `BadFunctions`' map: the matched `func`, its normalized `name` (borrowed from `KnownBadFunctions`), and its `kind`.
- `CallMarker<'a>`: Annotates an IDB, holding the context that marking needs: the `&'a IDB` itself, its `PltSegments` (built once in `run()`, lent to `BadFunctions::find_all()` and then moved into `CallMarker::new(&idb, plt)`, where only `traverse_xrefs()` uses it), and `bookmarked`, the set of addresses that already carry one of rhabdomancer's bookmarks (see below), so none of them is passed around as a parameter. `mark_all(&found)` iterates `found.iter()` (ignoring the function ID) and totals the counts returned by `mark_calls()` with `.sum()` over `Result<BookmarkIndex, IDAError>`, which stops at the first error; `run()` adds the `anyhow` context. `mark_calls()` receives each function's priority, name, and kind (printing `(thunk)` for `FunctionKind::Stub`, with an exhaustive `match`), formats the description (`[BAD n] <normalized name>`) itself, and returns the count from `traverse_xrefs()` (`0` for a function without XREFs); `traverse_xrefs()` counts newly added bookmarks with `saturating_add`. Keep IDB-dependent marking state (e.g., a visited set for thunk cycles) here rather than in `BadFunctions`. Idempotency: `CallMarker::new()` builds `bookmarked` from every bookmark index (`get_address(idx)` + `get_description_by_index(idx)` containing `PREFIX`), and `traverse_xrefs()` marks an address only if `self.bookmarked.insert(from)` succeeds, which also records the bookmarks added during the run, so a call site reached through several bad functions is bookmarked once. Never look a bookmark up by address (`get_description(ea)`): IDA overlays bookmarks added at an already bookmarked address, and a lookup by address returns only one of them, which may be a user's own; that made rhabdomancer re-mark such call sites on every run and even twice within one (pinned by `test_user_bookmark_at_call_site()`). The marking methods take `&mut self` because the set is updated during the walk. Comments don't need this: the `get_cmt(from)` check sees the whole comment text. Both checks deliberately use `contains(PREFIX)`, not `starts_with`: for comments it's required, because the tag is added after any existing comment; for bookmarks it keeps one of rhabdomancer's bookmarks that a user edited by prepending text recognized (so it isn't marked again), at the cost of a user's own bookmark that merely mentions the prefix counting as rhabdomancer's. Every version has written descriptions starting with `[BAD `, so either check recognizes older IDBs. The tag is appended by hand (a `match` on `get_cmt`: `set_cmt` with the tag alone if there's no comment, nothing if it's already tagged, and otherwise the result of `append_tag()`, the existing comment, a newline, and the tag), not with IDA's `append_cmt`: when the address is a function's start, `append_cmt` appends to the function comment instead (with a regular comment as with a repeatable one; `set_cmt` doesn't redirect; undocumented: `bytes.hpp` describes `append_cmt` as appending to the same indented comment that `set_cmt` sets), which the `get_cmt(from)` check doesn't see, so such call locations had no instruction comment and got the tag appended to the function comment again on every run. A call location is a function's start when a wrapper's only instruction is a tail call to a bad function: `operator delete` (`??3@YAXPEAX@Z`, just `B free`) in `cmd.exe`, and `-O2` builds of `void xfree(void *ptr) { free(ptr); }` for arm64 Mach-O and x64 PE (mingw); unoptimized test binaries have none, which is why `check_comments_match_bookmarks()` never caught it. Appending by hand gives the same text as `append_cmt` elsewhere, as compared in IDAPython on IDA 9.5 away from function starts: the tag alone for no or an empty comment, otherwise the existing text unchanged (no trimming, trailing newlines and whitespace kept), a newline, and the tag. Repeatable comments were rejected (`append_cmt` redirects them too, and IDA shows them wherever the address is referenced, so a tag in a repeatable function comment would appear at every caller of the wrapper), and so were anterior lines (not exposed by idalib, numbered slots to manage, and a different place for the tag than in every other IDB). IDBs annotated by earlier versions keep their tags in such function comments, and a re-run adds the instruction comment once without removing them. IDA stores at most 1024 bytes of a comment (`MAX_COMMENT_LEN`, the SDK's `MAXSTR`; measured in IDAPython on IDA 9.5: 1024 bytes of UTF-8 are kept, longer comments are cut at a character boundary, and `set_cmt` and `append_cmt` still report success), so appending the tag to a user's comment of more than 1024 bytes minus the tag and the newline used to cut the tag short, leaving a fragment such as `\n[BA` in the user's comment and no tag (on every run, without the comment growing; `append_cmt` did the same). `append_tag()` returns `None` in that case, and `traverse_xrefs()` leaves the comment unchanged and prints ``[!] Warning: comment at <addr> is too long to add `<tag>` `` to stderr instead: the location keeps its bookmark, and the warning is repeated wherever the location is listed and on every run, since it never gets its tag. Pinned against IDA's real limit by `test_user_comment_at_comment_limit()` (a 1009-byte user comment gets the tag, ending at exactly 1024 bytes, and a 1010-byte one stays unchanged), which fails if `MAX_COMMENT_LEN` is off by one either way or if IDA keeps fewer bytes (but not if a future IDA keeps more, which would only cause needless warnings); the `append_tag_joins_with_newline_within_ida_limit` unit test pins the boundary, in bytes, with ASCII and 2-byte characters.
- `Priority` enum: `High`/`Medium`/`Low` — maps to BAD 0/1/2. Variants are declared from highest to lowest priority, and the derived `Ord` follows declaration order (no explicit discriminants or `#[repr]`), which is what orders `BadFunctions`' map: keep this order when editing the enum. `level()` maps each variant to its tag digit with an explicit `match` (deliberately not a cast, so tags don't depend on declaration order), and `description()` builds `[BAD n] <name>` as `format!("{PREFIX}{}] {func_name}", self.level())`, so tags are derived from the `PREFIX` constant and can't drift from it. The `description_formats_tag_and_name` unit test pins the full format with literals.
- `CallMarker::traverse_xrefs(target, desc)`: Iteratively walks the XREFs to `target` with a worklist of addresses: each popped address's chain is walked with `for xref in iter::successors(first_xref_to(addr, ...), XRef::next_to)` (an address without XREFs yields nothing, so `mark_calls()` just passes `func.start_address()`). Handles `.plt` thunk indirection for ELF binaries: when an XREF comes from a `.plt` segment, the containing thunk's start address (`function_at(from).map(|func| func.start_address())`, no `BADADDR` sentinel) is queued and its XREFs walked after the current chain; the explicit worklist keeps deep indirection from overflowing the call stack. A `visited` set, seeded with `target`, makes each address queued at most once. That fixes a real bug: when a `.plt` stub references the import more than once, as IDA sees AArch64 stubs (`tests/data/double_xref`), the stub's XREFs were walked once per reference, listing its callers twice (pinned by `test_thunk_with_repeated_xrefs()`). It also makes cyclic `.plt` references terminate. Such cycles don't occur in compiler-generated binaries as IDA analyzes them (on `tests/data/ls`, IDA splits every lazy-binding `.plt` stub into its own function, and nothing the walk visits is referenced from them; the 47 `jmp PLT0` XREFs form no cycle), but they can in crafted binaries or if IDA delimits `.plt` functions differently (e.g., one function spanning PLT0 and the stubs would reference itself), and rhabdomancer runs on untrusted input. The integration tests can't exercise the cycle case; it was checked by forcing a self-cycle (terminates with the guard, hangs without it). Call-site order is not a contract: a chain's direct callers are listed before the callers reached through its thunks (on `tests/data/ls` imports have no direct callers, so the output matches the earlier recursion-like order). XREFs are queried with `XRefQuery::FAR`, not `ALL`, so ordinary-flow XREFs (the previous instruction falling through into `addr`) are skipped: compilers reach another function with calls or jumps (tail calls included), which `FAR` keeps, while a fall-through into a function's start is alignment padding or follows a call that never returns; on `tests/data/static_glibc`, `ALL` marked 4 such false call sites (`nop` padding at the end of `wcsrtombs` and `_mid_memalign`, and `bl __libc_assert_fail` at the end of `__malloc_arena_thread_freeres` and `realloc`), and `FAR` changed nothing on the other binaries checked. Hand-written assembly that deliberately falls through into a bad function's entry would now be missed, which is accepted (its meaningful call sites are the callers of the function that falls through, which `ALL` didn't mark either). Early `continue`s (for `.plt` and non-code XREFs) avoid an `if`/`else if` without `else`. `self.idb.bookmarks()` (a zero-cost `PhantomData` wrapper) is bound once per traversal.
- `PltSegments`: The address ranges of all `.plt*` segments of the IDB, collected once by `PltSegments::new()` in `run()` and shared by `find_all()` (for `is_stub()`) and `CallMarker` (to follow `.plt` stubs) (no per-call FFI lookups). `contains()` checks whether an address falls within any of them; the ranges are half-open `Range<Address>` values, matching IDA's `range_t` (`end_ea` excluded), which unit tests pin without an IDB.
- `is_stub(func, plt)`: The single definition of a stub, computed once per matched function in `find_all()` and used for `lookup()` (where IDA's numeric suffix may be stripped) and for the `(thunk)` label: a function IDA flags as a thunk (`FunctionFlags::THUNK`) or that starts in a `.plt` segment. Both checks are needed: ELF lazy-binding stubs in `.plt` aren't flagged (the real stubs in `.plt.sec` are), while Mach-O `__stubs` and PE `jmp [__imp_X]` stubs are flagged but not in `.plt`. It replaced two separate notions (the THUNK flag for matching, `.plt` for labeling); unifying them changed no call-site count on any binary checked (`ls`, `double_xref`, `no_calls`, `import_stubs`, two Mach-O and two PE builds of a test program, two `-O2` builds of a tail-call wrapper, and `cmd.exe`), only added `(thunk)` to PE and Mach-O stub headers. `traverse_xrefs()` deliberately still follows only `.plt` stubs, which leaves thunks elsewhere unhandled: IDA flags MSVC incremental-linking thunks (`j_memcpy`, ...) in debug builds as thunks, and also the wrapper in a fully stripped build of `int run(const char *cmd) { return system(cmd); }`, called twice from `main`, with `x86_64-w64-mingw32-gcc -O2 -s` (named `j_system`; with symbols, it keeps the name `run` and isn't flagged). For those, only the jump inside the thunk is listed and marked, and its callers are missed (on that stripped build, 18 locations instead of 20; on an MSVC x64 incremental debug build, 4 instead of 8, every real caller of an import missed). A branch that also followed (and marked) code XREFs from stubs outside `.plt` fixed this, but was dropped to keep the code lean, since such thunks mostly occur in debug builds; it's a TODO in the README (see the `j_` note below).
- `strip_decorations()`: Strips the decorations that platforms add to the symbol of the same function, before any other step of `lookup()`, so that the alias prefixes and the IDA suffix are recognized in decorated names too (`#_o_malloc` gives `_o_malloc`, which then matches `malloc`). `TryFrom` applies it to configuration names too, before `normalize_name()`, so that both sides stay symmetric: a configured `#memcpy` matches both `#memcpy` and `memcpy`, `"#"` is rejected as empty, and `#strcpy` and `strcpy` under different priorities are reported as duplicates; without it, such entries were accepted but could never match. Three kinds of decorations, the ARM64EC marker, Apple's variant suffixes, and the size of the arguments of 32-bit x86 functions (see the end of this entry). `ARM64EC_MARKER`: Microsoft's toolchain prefixes the native version of a C function in ARM64EC/ARM64X binaries with `#` (C++ functions get `$$h` inside the mangled name instead, irrelevant here). IDA 9.4 and earlier replaced the `#` with `_` (`_memcpy`, which `normalize_name()` handled), but IDA 9.5 keeps names verbatim by default (`GarbleNames = 0` in `IDA.CFG`), so on the ARM64 `cmd.exe` (an ARM64X binary) rhabdomancer marked 236 call locations instead of 301 (`memcpy`, `memmove`, `calloc`, `free`, `malloc`, `wpopen`, and `ShellExecuteExW` lost every call site); with the marker stripped, it marks the same 301 call sites as on IDA 9.4. Exactly one leading `#` is stripped, matching the convention. It's a separate step rather than part of `normalize_name()` (which would trim any mix of leading `#`, `.`, and `_`, and would leave `strip_alias_prefix()`, which needs the raw name, blind to `#_o_malloc`) or an entry in `ALIAS_PREFIXES` (which would let the IDA suffix be stripped from every native ARM64EC function, e.g., a helper `#read_16` matching `read`, and would leave `#_o_malloc` unmatched, since only one alias prefix is stripped). So a `#X_N` name only matches if it's a stub (IDA 9.5 doesn't flag the `#` functions as thunks), which is accepted: `cmd.exe` has no `#X_N` names on IDA 9.5, since the `_N` names of IDA 9.4 came from the garbled `_X` colliding with an existing `_X`, and two functions named `#X` are needed for one now. Deliberately not matched: ARM64EC exit and entry thunks (`#strcpy$exit_thunk`, `$iexit_thunk$...`, `__iexit_thunk_for_@CreateProcessW`), which have no call XREFs (the call sites are found through the stubs), and `__impchk_X`/`__imp_load_X` helpers (295 and 17 in `cmd.exe`, with no call sites). IDA 9.5 doesn't flag the `#` functions as thunks, so they're listed without `(thunk)`. No other character is affected by IDA 9.5's change: IDA 9.4 already kept `$`, `:`, `?`, and `@` verbatim (for `$` suffixes, see `APPLE_VARIANT_SUFFIXES` below, and for `@`, `X86_ARGS_SIZE_SEPARATOR`), and the other characters IDA 9.5 now keeps (spaces, `'`, `` ` ``, `<>`) only appear in demangled C++ special names (`` `dynamic initializer for '...'' ``), which can't match C names; names were identical on IDA 9.4 and 9.5 in i686 and x86-64 mingw builds (`_vuln_std@8`, `@vuln_fast@8`), Mach-O stubs (`_realpath$DARWIN_EXTSN`), and the ELF test binaries (IDA includes no symbol version such as `@GLIBC_2.14` in function names). Setting `GarbleNames` when opening the IDB was rejected, since rhabdomancer saves the IDB and would change the names users see in it. No integration test covers the marker: `cmd.exe` can't be redistributed, and a clang ARM64EC object (`--target=arm64ec-pc-windows-msvc -c`) doesn't reproduce the naming (its extern references aren't functions), while a linked ARM64EC executable needs `lld-link`. Verify it by hand whenever `lookup()` or `strip_decorations()` changes: run rhabdomancer on the ARM64 `cmd.exe` (kept outside the repository) with IDA 9.5 and check that it marks 301 call locations (236 without the marker stripped). `APPLE_VARIANT_SUFFIXES`: Apple's SDK (`sys/cdefs.h`, the `__DARWIN_SUF_*` macros) appends `$1050`, `$DARWIN_EXTSN`, `$INODE64`, `$NOCANCEL`, or `$UNIX2003` to the symbols of libc functions to select a variant, chained in several orders (e.g., `__DARWIN_ALIAS_C` gives `open$NOCANCEL$UNIX2003`, `__DARWIN_1050ALIAS_I` gives `fstat$1050$INODE64$UNIX2003`), so all of them are stripped from the end, repeatedly. IDA has always kept them verbatim (`$` was already allowed in IDA 9.4), so such stubs were never matched, regardless of the IDA version: on current macOS, `syslog$DARWIN_EXTSN` and `realpath$DARWIN_EXTSN` are common even in arm64 system binaries, and `stat$INODE64`, `fstat$INODE64`, and `lstat$INODE64` in x86-64 ones (counted in `/bin`, `/usr/bin`, and `/usr/sbin`: `stat` 278, `fstat` 200, `syslog` 175, `realpath` 133, `lstat` 120), and on `tests/data/darwin_variants` rhabdomancer marked 1 of the 4 calls. Only these exact, case-sensitive suffixes are stripped, so other `$` names (`#strcpy$exit_thunk`, ncurses' `$NCURSES60`, Objective-C and Swift symbols) stay unmatched; a suffix followed by IDA's numeric suffix (`_stat$INODE64_0`) isn't stripped either, which is accepted, since a Mach-O binary has one stub per imported symbol, so stub names don't collide: on IDA 9.5, no suffixed name carried IDA's suffix in `/usr/bin/stat` (including its x86-64 slice, with `_stat$INODE64`, `_fstat$INODE64`, `_lstat$INODE64`, and `_realpath$DARWIN_EXTSN`), `/bin/ls`, `/usr/bin/find`, `/usr/bin/du`, `/bin/realpath`, `/usr/bin/logger`, and `tests/data/darwin_variants`. `X86_ARGS_SIZE_SEPARATOR`: on 32-bit x86, MSVC and mingw append `@` and the size of the arguments in bytes to the symbols of `stdcall` functions (`_WinExec@8`, every Win32 API), `fastcall` ones also prefix the name with `@` (`@f@8`), and `vectorcall` ones double the separator (`f@@8`), so one trailing `@<digits>` is stripped, then either a trailing `@` (`vectorcall`) or a leading one (`fastcall`); the leading `@` is only stripped together with the suffix, so a lone `@f` stays unmatched. The digit check is shared with `strip_ida_suffix()` through `strip_number_after(name, separator)`. Cutting at the first `@` was rejected: MSVC's C++ names contain `@` (`?f@@YAXXZ`) without ending in digits, and the narrower rule leaves them alone (IDA includes no ELF symbol version such as `@GLIBC_2.14` in names, see above). Like Apple's suffixes, it isn't an IDA 9.5 regression: both IDA 9.4 and 9.5 keep `@`, so such stubs were never matched. It matters for 32-bit binaries with symbols that call `stdcall` functions through import stubs: on `tests/data/stdcall_stubs` (with symbols), IDA names the stubs `_WinExec@8`, `_lstrcpyA@8`, and `_LoadLibraryA@4`, and rhabdomancer marked 16 call locations instead of 19, while a fully stripped build of the same source names them `WinExec` etc. and always matched. Calls through `<windows.h>`'s own declarations are another matter: they're `dllimport`, so they go through the import address table and are missed regardless (see the IAT note under IDA integration notes). An argument size followed by IDA's numeric suffix (`_WinExec@8_0`) isn't stripped, which is accepted: IDA adds that suffix when a name is taken, and in x64 PE builds a stub's plain symbol collides with the name IDA gives the import (hence `strcpy_0` in `import_stubs`), but in 32-bit ones the stub's symbol is decorated (`_WinExec@8`) and the import isn't (`WinExec`), so a suffix needs two functions with the same decorated name (none in the fixture). Pinned by `lookup_strips_x86_argument_size`, which also pins that the suffix gate still applies to decorated names (`_read_16@4` matches `read` only as a stub) and that the argument size is stripped before the alias prefixes (`__o_malloc@4` matches `malloc`).
- `normalize_name()`: Strips leading dots/underscores from function names for cross-platform matching.
- `strip_alias_prefix()` and `strip_ida_suffix()`: The fallbacks used by `lookup()`, each returning `None` when there's nothing to strip. `strip_alias_prefix()` takes the raw name and strips the first matching prefix in `ALIAS_PREFIXES` (`__o_`/`_o_` for Universal CRT wrappers, `__libc_` and `__GI_` for glibc aliases, `__isoc99_` and `__isoc23_` for glibc's redirects), normalizing the rest (`__o_malloc` gives `malloc`, `__o__wpopen` gives `wpopen`, `__libc_system` gives `system`, `__GI___snprintf` gives `snprintf`); it checks the raw name because the leading underscores tell an alias apart from a function such as `o_write` or `libc_system`. A single leading dot is ignored first, for every function kind: IDA names ELF `.plt` stubs with one (`.__isoc23_sscanf`), and on PPC64 ELFv1 `.name` is a function's code, so a dotted alias is the same alias, just as `normalize_name()` ignores leading dots for every other name. Without it, the raw-name check matched only the import of an alias, not its stub: the call sites were still found through the import's walk of its stub, but listed once, and lost if IDA doesn't link the stub to its import, the very case for which stubs and imports are both kept (see `BadFunctions`); with it, an alias stub matches by name like every other ELF stub, giving both paths (on `tests/data/ls`, `.__isoc23_strtol` and `__isoc23_strtol` both match a configured `strtol`). Ignoring it for stubs only was tried and dropped: it missed PPC64's dotted aliases (`.__libc_system` is `system`'s code there), which are real matches, not false ones. Configuration names deliberately don't get alias prefixes stripped (unlike decorations): mapping them in `TryFrom` was tried and dropped, because a configured name that merely starts with a prefix (e.g., `__libc_start_main`, a glibc internal, not an alias) was stored as `start_main`, mislabeling its matches and matching unrelated `start_main` functions, while `lookup()` tries the exact name first, and because custom configurations listing an alias and its base name under different priorities (e.g., `system` and `__libc_system`) were rejected. So such configurations keep both entries, each matching exactly. glibc's headers redirect calls to the `scanf` family to `__isoc99_*` names (to its C99 behavior) and, since glibc 2.38, in C23 mode (GCC 15's default), the `scanf` and `strtol` families to `__isoc23_*` names, so those calls were missed unless the configuration listed the redirected name: the built-in one used to list the six narrow `__isoc99_*` `scanf` functions, each at the same priority as its base name, whose exact matches labeled C99 calls `isoc99_sscanf` while C23 ones were labeled `sscanf`, so they were removed from it: every variant is now labeled by its base name (on `fermion-wrapper`, `__isoc99_sscanf` and `__isoc99_fscanf` are labeled `sscanf` and `fscanf` instead of `isoc99_sscanf` and `isoc99_fscanf`, with the same 159 call locations). A custom configuration that lists a redirect still matches it exactly and keeps that label, since configuration names don't get alias prefixes stripped. `tests/data/ls` has `.__isoc23_strtol` and `__isoc23_strtol` (`strtol` isn't in the built-in configuration, so no pinned count changed; with a configuration listing only `strtol`, its stub and import now both match and its 1 call site, which was missed before, is marked), and `tests/data/static_glibc` has only `__isoc23_*` functions that aren't configured (`strtoumax`, `strtol_l`, `strtoul_l`), one of them also as `__isoc23_strtoumax_0`, a non-stub function in `.text` with IDA's numeric suffix, which is why redirects count as library aliases for the suffix gate (the example in `lookup()`'s doc comment); building a fixture with `__isoc23_` `scanf` calls needs a Linux toolchain with glibc 2.38 or later, so the prefixes are pinned by unit tests and by `strtol` on `ls` in `test_custom_configuration()` (14 marks, 13 without the `__isoc` prefixes). The glibc prefixes matter in statically linked binaries, where `system` and `__libc_system` (or `snprintf` and `__GI___snprintf`) are symbols at the same address and IDA may pick the alias: on `tests/data/static_glibc`, `main`'s only call to `system` was missed because IDA names the function `__libc_system`, and `realloc` (`__libc_realloc`, 16 calls inside glibc) and `snprintf` (`__GI___snprintf`, 1) were missed too (742 marks instead of 760, both counts including 4 fall-through false positives that `XRefQuery::FAR` later removed). `do_system`, glibc's internal implementation called only by `__libc_system`, deliberately isn't matched. Other glibc-decorated names (`_IO_*`, `__printf_buffer_*`, `__*_nocancel`, IFUNC variants such as `__memcpy_generic`) are internals, not aliases, and aren't matched either. `strip_ida_suffix()` strips one `_<digits>` suffix (via `strip_number_after()`, shared with `strip_decorations()`), which IDA appends when a name is already in use (e.g., `memset_0`, `CreateProcessW_0`). Without them, such PE import stubs were never matched: on an MSVC ARM64 `cmd.exe`, rhabdomancer marked 104 call locations instead of 301 (166 calls through `memset_0` alone), and on `tests/data/import_stubs` 10 instead of 22. IDA adds the suffix only when the plain name is taken (e.g., by a symbol), which is why the same stub can be named `memcpy` in one build and `memcpy_0` in another. The suffix is only stripped from stubs and library aliases because 121 built-in names are short plain words (`read`, `write`, `free`, `stat`, ...), so stripping it from any function would match helpers such as `read_16`; every suffixed match found in `cmd.exe` and `tests/data/import_stubs` is a thunk, and the three non-thunk ones are UCRT wrappers (`__o_malloc`, `__o__wpopen`, `_o_rand_0`; IDA 9.5 names the first two `#_o_malloc` and `#_o__wpopen`, see `strip_decorations()`), so the gate loses none of them; that's why library aliases count as stubs for this gate: without them, `_o_rand_0` (not a thunk) wouldn't match, and `cmd.exe` would lose the 2 calls to `rand` in its own `GetEnvVar` (299 marks instead of 301 with a stubs-only gate). Deliberately a fallback in the name lookup rather than a different design: matching from the `__imp_X` entries would also catch direct `call [__imp_X]` calls (none in the binaries checked) but needs a rule for which referencing functions are stubs, and `Function::calc_thunk_target()` returns `None` for every ARM64 thunk in `cmd.exe`. A thunk named like `strcpy_2` that isn't a `strcpy` stub would still match, which is accepted. Not handled: IDA's `j_` prefix of MSVC incremental-linking thunks (`j_strcpy`), whose callers are missed because only `.plt` stubs are followed (a deliberate choice, see `is_stub()`). Fortified `__X_chk` functions (`_FORTIFY_SOURCE`, e.g., `__memcpy_chk`, `__memset_chk`, and `__snprintf_chk` in `tests/data/ls`, `___strcpy_chk` in Mach-O builds) are deliberately not matched, as the checked variants of the listed functions, and the README says so: users who want them add the `__X_chk` names to a custom configuration (on `ls`, adding those three to `medium` marks 110 call locations instead of 86). Don't strip `_chk` in `lookup()`.
- `function_name()`: Returns a function's name, or `[no name]` if it has none; a private copy of haruspex's `function_name()` (same fallback text), rather than a haruspex dependency for a one-liner. Caller names are printed as `{from:#X} in {}` (or `{from:#X} (lib) in {}` for library code) with `function_name(&func).escape_debug()`, since they come from the binary (terminal escapes, bidi overrides), the same technique as haruspex and augur; an XREF outside any function prints the `[unknown]` literal, without allocating. The bad-function headers print the normalized name from the configuration, which isn't escaped.

## Output

Results go to stdout (`println!`); everything else (banner, progress, summary, timing, errors) goes to stderr (`eprintln!`), with the prefixes `[*]` for progress, `[+]` for success and summaries, `[-]` for information, and `[!]` for warnings and errors, and the elapsed time as `{:.1} seconds`. Preserve this split when adding new output. The results are the bad-function headers and call-site locations.

stdout layout:

```
                                  # blank line before each bad function
[BAD {level}] {name} (thunk)      # ` (thunk)` only for stubs (see `is_stub()`)
{addr:#X} (lib) in {caller}       # one line per call site, `[unknown]` outside any function,
                                  # ` (lib)` only if IDA flags the caller as library code
...
```

The ` (lib)` label marks call sites in functions that IDA recognizes as library code (`FunctionFlags::LIB`, from FLIRT signatures), typically in statically linked runtimes, so that users can filter them out (e.g., `grep -v '^0x[0-9A-F]* (lib) in '`). It comes before the caller name rather than after it: the name comes from the analyzed binary, so a function named, e.g., `vuln (lib)` could otherwise fake the label and hide a real call site from such a filter, while the address can't contain it; the README only mentions the label, not this filter, and such a filter may also hide calls from user code that reach a bad function only through library code (e.g., through a thunk or wrapper outside `.plt` that IDA flags as library code, whose callers aren't followed); they are still marked in the IDB, and there's no option to skip them yet (a README TODO). It's only a label: a fuller version that also counted them separately in the summary (`MarkCounts` with an `iter::Sum` impl) was dropped as not worth its code, since IDA only recognizes runtimes it has signatures for (in IDA 9.4: Visual C++ for x86 and x64, Go's standard library, and a few others, but nothing that matched the ARM64 MSVC `cmd.exe`, and no glibc for ARM64), so nothing was flagged on any binary checked (`ls`, `static_glibc`, `cmd.exe`, Mach-O and mingw builds); IDA 9.5 added ARM64 MSVC signatures, which flag a few runtime functions in `cmd.exe` as library code, so 1 of its 301 call sites (in `memcpy_s`) is now labeled, while nothing changed on the test binaries; for other runtimes, apply suitable signatures in IDA first and run rhabdomancer on that IDB. No test binary has call sites in library code, so the label is verified by hand only (it was exercised by temporarily checking `FunctionFlags::THUNK` instead).

The label deliberately stays `(thunk)`, although the code calls the concept a stub (`is_stub()`): it's IDA's own term (the THUNK flag, `j_` names), and it has been in the output since v0.1.0, so scripts may rely on it. `stub` is used internally only because `is_thunk` would suggest IDA's flag alone, while `is_stub()` also covers `.plt` functions that IDA doesn't flag.

Each call site is also annotated in the IDB with a bookmark and a comment `[BAD n] <normalized name>`, where `n` is the priority level (0 = high, 1 = medium, 2 = low). The annotation text is an external contract, documented in the README: users and scripts search IDBs for it, and IDBs annotated by previous versions carry it, so never change it.

## Configuration

All "bad" functions are defined in `conf/rhabdomancer.toml`, grouped into `high`, `medium`, and `low` arrays. The file is embedded in the binary at build time as `DEFAULT_CONFIG` (`include_str!`), replacing the earlier path built from `CARGO_MANIFEST_DIR`, which broke binaries whose source tree was moved or deleted (e.g., after `cargo install`); editing it requires a rebuild. A custom configuration file can be used instead by setting the `RHABDOMANCER_CONFIG` environment variable to its path. `conf/` must stay in the published package (not in `Cargo.toml`'s `exclude`), since `include_str!` needs it when building from crates.io. The loader reads the file with `fs::read_to_string` and deserializes it with the `toml` crate (`toml::from_str`, features `std`, `serde`, and `parse` only) via serde; the parse error type is imported as `TomlError`. Each name may appear under only one priority (a leading ARM64EC `#`, Apple's variant suffixes such as `$INODE64`, the size of the arguments of 32-bit x86 names such as `@8`, and leading dots/underscores are ignored when comparing names); otherwise loading fails with an error naming the (normalized) duplicate. Repeats within the same priority are harmless and merged. The built-in list holds no entries that normalization or the alias prefixes already cover: it lists each function once, and a decorated spelling such as `_mbscpy` or `_snwprintf` remains only where no other spelling of the same function is listed (they're the functions' real MSVC names). The `default_configuration_has_no_redundant_entries` unit test enforces it: no entry may start with an alias prefix, and no two entries may be the same once decorations and leading dots/underscores are removed. Until 1.1.0 it mirrored another tool's list verbatim and also held 69 decorated duplicates (e.g., `_strcpy` next to `strcpy`, two of them repeated) and the six `__isoc99_*` `scanf` redirects; removing them changed no key's priority and no call site (checked on `ls`, `static_glibc`, `double_xref`, `import_stubs`, `darwin_variants`, `cmd.exe`, and `fermion-wrapper`), only the labels of the `__isoc99_*` redirects (see `strip_alias_prefix()`). The 20 `<tchar.h>` names (`_tcscpy`, `_tcsncpy`, `_stprintf`, `_tmakepath`, ...) stay on purpose, even though most are macros that the compiler expands to configured functions: in `_MBCS` builds without `_MB_MAP_DIRECT` (the default), `_tcsncpy`, `_tcsncat`, `_tcstok`, and `_tccpy` are real functions imported from the CRT ("type-safe linked-in function thunks", per mingw-w64's `tchar.h`), which only these entries match, and the other 16 (14 macros in mingw's header, plus `_tccat` and `_gettws`, which it doesn't define at all) were kept too, since Microsoft's own header couldn't be checked and dead entries cost nothing. Two of them are `high` while one of their wide expansions is `medium` (`_stprintf` and `_vstprintf`, which expand to `sprintf`/`vsprintf` or to MSVC's legacy `_swprintf`/`_vswprintf`), which only matters if such a name is a real function. Normalization merges MSVC's unbounded legacy `_swprintf`/`_vswprintf` into C99's bounded `swprintf`/`vswprintf` (`medium`), and its non-terminating `_snprintf` into `snprintf` (`medium`), a known imprecision of matching by normalized name. Possibly a larger gap, not yet verified: since Visual Studio 2015, the Universal CRT defines the `printf` and `scanf` families as inline functions in its headers, which call imported `__stdio_common_*` functions (`__stdio_common_vsprintf`, `__stdio_common_vswprintf`, `__stdio_common_vsscanf`, ...) and select the variant (e.g., `sprintf` vs. `snprintf`) through their arguments (option flags, buffer count) rather than their name. So in a stripped MSVC `/MD` release build, where the wrappers are likely inlined, calls to these functions may only reach `__stdio_common_*` imports, which no configured name matches. `cmd.exe` doesn't show this, since it imports the old `msvcrt.dll`, where these functions are real exports. A configuration entry wouldn't help much either, because one `__stdio_common_*` function covers both bounded and unbounded variants, which only differ in their arguments. The same MSVC x64 `/MD` release build needed for direct IAT calls (see IDA integration notes) would measure both. Entries that are empty once normalized (e.g. `""`, `"_"`, `"."`, `"#"`, `"$UNIX2003"`, `"@8"`) are also rejected, with an error showing the original spelling. All three arrays are required, and any other key is rejected (`deny_unknown_fields`), so a typo can't silently drop a priority's functions.

## Error handling

- Functions below `run()` return concrete error types (`IDAError` from marking, `TomlError` from parsing); only `run()` and `KnownBadFunctions::load()`, which combines reading the file and parsing it, use `anyhow`, adding context.
- The configuration is loaded before the binary is opened, so a configuration error never creates an IDB.
- Marking stops at the first error (`CallMarker::mark_all()` sums over `Result`).
- Finding no calls is not an error: `run()` returns `Ok(0)`, since a re-run on an annotated IDB legitimately marks nothing (unlike augur and haruspex, which reject zero results, since their output would be empty).
- XREFs outside any function are printed as `[unknown]` and still marked.
- `main()` prints errors as `[!] Error: {err:#}` (the full context chain) and exits with `ExitCode::FAILURE`.

## Lint policy

All clippy lint groups (`all`, `pedantic`, `nursery`, `cargo`, `restriction`) are enabled as warnings in the workspace lints of `Cargo.toml` (the same configuration in augur, haruspex, and rhabdomancer) and treated as errors by `cargo clippy -- -D warnings`. A curated set of restriction lints is explicitly allowed (e.g., `implicit_return`, `question_mark_used`, `print_stdout`, `pattern_type_mismatch`), and `linker_messages = "allow"` silences linker warnings from IDA's Windows libraries (see <https://github.com/idalib-rs/idalib/issues/81>, closed with this suppression as the fix). Notably forbidden outside tests:

- `unwrap`, `expect`, `panic`, `todo`, `unimplemented`, `unreachable`, `dbg_macro`: use `?`, `anyhow` context, and `Option` combinators instead.
- Unsafe blocks without a `// Safety:` comment (`undocumented_unsafe_blocks`).
- Undocumented items (`missing_docs`, `missing_docs_in_private_items`): every item has a doc comment, private ones and test helpers included.

`clippy::min_ident_chars` is enabled, so single-character identifiers (e.g. `|s|`, `for f in`) are flagged — use descriptive names like `name`, `func`, `idx`. Clippy's default `allowed-idents-below-min-chars` still permits `i`, `j`, `x`, `y`, `z`, `w`, and `n`, and parameters that keep a trait's own name (such as `f` in `fmt::Display::fmt`) are not flagged either; prefer descriptive names (e.g. `idx`) anyway.

Pure functions whose result matters carry `#[must_use]`, private ones included (clippy's `must_use_candidate` only flags public items), e.g., `Priority::level()`, `KnownBadFunctions::lookup()`, `PltSegments::contains()`, `function_name()`, and `normalize_name()`.

Use `#[expect(clippy::some_lint, reason = "...")]`, never `#[allow]`, to locally suppress a lint that genuinely cannot be avoided, in both library code and tests. The only one in the codebase: `panic_in_result_fn` (test assertions, as a module-level `#![expect]` in `tests/main.rs` and on `mod tests` in `src/lib.rs`). `env::set_var`/`remove_var` are `unsafe` in Rust edition 2024; wrap them in `unsafe {}` with a `// Safety:` comment explaining the single-threaded context, as `main()` and `run_with_config_path()` in `tests/main.rs` do.

Taplo enforces TOML formatting (`.taplo.toml`: 120-char line width, 4-space indent).

The crate-level documentation in `src/lib.rs` is assembled in a specific order to satisfy two restriction lints simultaneously, and should not be "simplified" back to a plain `#![doc = include_str!("../README.md")]`:

- `#![doc = env!("CARGO_PKG_DESCRIPTION")]` is always present (pulls the `description` from `Cargo.toml` with no duplication) so the crate is documented in every build configuration — this satisfies `missing_docs`, which runs without `--cfg doc`.
- `#![cfg_attr(doc, doc = include_str!("../README.md"))]` pulls in the README only under `cfg(doc)`, satisfying `clippy::doc_include_without_cfg`.
- The `#![doc = ""]` between them forces a Markdown paragraph break so the description and the README's leading heading don't merge.

### Integration tests

`tests/main.rs` holds the custom-harness integration tests, structured like augur's: documented constants at the top, a `main()` that calls `idalib::force_batch_mode()` and then one `test_*` function per scenario (in augur's and haruspex's order: the successful runs, then the failures), and one `check_*` function per assertion (each printing its own `[*] Checking ... Ok.` line). Scenarios:

1. `test_default_configuration()` (against `tests/data/ls`): runs the real binary (via `run_binary()`, as augur's and haruspex's first scenarios do, pinning the CLI output in the same analysis) and checks, with literals: success; stdout line counts by kind (`check_number_of_output_lines()`: `N_BAD_FUNCTIONS` = 20 blank lines and 20 `[BAD n]` headers, `N_CALL_SITE_LINES` = 172 call-site lines, i.e., the 86 locations listed under both stub and import, and nothing else); the whole line `0x2C5F in sub_2C30` (`check_stdout_line()`); the whole stderr summary line `[+] Marked 86 new call locations` (`check_summary()`); and with `check_priority_order()` that the levels of the `[BAD n]` headers never decrease (high, then medium, then low) and that more than one level appears (on `ls`: medium, then low), so the check isn't vacuous (the `Priority` unit test pins only the enum's order; this pins that the output follows it, and reversing `BadFunctions::iter()` fails it). It then checks bookmark count (`N_MARKS`), that every bookmark description starts with `BAD_PREFIX`, comment count, and that the comment at every bookmarked address starts with that bookmark's description, and finally runs `rhabdomancer::run()` again on the same IDB and asserts 0 new marks (idempotency lives here because it depends on this scenario's IDB). `run()`'s return value on new marks is checked by scenarios 2, 9, 10, 11, and 12.
2. `test_custom_configuration()`: runs with `CUSTOM_CONFIG_TOML` via `RHABDOMANCER_CONFIG`, asserts exactly 14 marks, and runs the same bookmark count, comment count, and comment-matches-bookmark checks as scenario 1, plus an exact check that every bookmark description is `[BAD 1] ` followed by one of the normalized names in `CUSTOM_MEDIUM`. Since the custom config includes decorated names (`_fwrite`, `.memset`), this verifies that both bookmarks and comments use normalized names. It also lists `strtol`, which `ls` only calls as glibc's C23 redirect `__isoc23_strtol` (1 call site, so 13 marks without the `__isoc` prefixes), to pin the alias prefixes on a real binary, with a `[BAD 1] strtol` bookmark required (`check_bookmark_exists()`, so that losing `strtol` fails even if another change kept the count at 14; shown to fail on its own with the prefixes removed and the count check skipped), and checks that `.__isoc23_strtol` exists (`check_function_exists()`, by name only, since IDA flags `.plt.sec` stubs as thunks but not lazy-binding `.plt` ones), which guards the naming that the unit tests of the dotted alias stubs assume (the in-process run doesn't capture stdout, where the `(thunk)` header would show the stub match).
3. `test_binary_without_calls()`: runs against `tests/data/no_calls`, a minimal macOS arm64 Mach-O binary built from `tests/data/no_calls.c` (`cc -O0 -o no_calls no_calls.c`, the same binary as augur's `no_strings`), and asserts 0 marks, 0 bookmarks, and 0 comments.
4. `test_thunk_with_repeated_xrefs()`: regression test for duplicated call-site lines. Runs the real `rhabdomancer` binary (`env!("CARGO_BIN_EXE_rhabdomancer")`, via `run_binary()`, with `RHABDOMANCER_CONFIG` removed) against `tests/data/double_xref`, an ARM64 ELF whose `main` calls `system` through `system@plt`, checks that it succeeds, and pins its exact stdout (`DOUBLE_XREF_LISTING`): IDA sees the AArch64 stub (`adrp`/`ldr`/`add`/`br`) referencing the `system` import more than once, so without `traverse_xrefs()`' visited set the stub's XREFs were walked once per reference and `0x7F4 in main` was listed twice. The bookmark check already deduplicated the marks, so only the stdout listing shows the bug, which is why this scenario captures stdout through a subprocess (`rhabdomancer::run()` prints it directly). It also checks 1 bookmark, 1 comment, and comments matching bookmarks. The listing shows `system` twice (thunk and import), which is deliberate (see `BadFunctions`).
5. `test_import_stubs_with_numeric_suffix()`: regression test for PE import stubs that IDA names with a numeric suffix. Runs the real binary against `tests/data/import_stubs`, an x86-64 PE built with mingw from `tests/data/import_stubs.c` (build command in the source; renamed without `.exe`, since IDA names the IDB of `foo.exe` `foo.exe.i64`, which `reset_idb()` wouldn't remove) and stripped of debug info only: its symbols take the plain names, so IDA names the stubs `strcpy_0`, `system_0`, `memcpy_0`, `malloc_0`, and `getenv_0` (a fully stripped build has no `_0` names, so it wouldn't test anything). Checks success, that `strcpy_0` exists and is a thunk (`check_thunk_exists()`, so the scenario fails loudly instead of passing vacuously if a future IDA names the stubs differently), the `[BAD 0] strcpy (thunk)` header (`strcpy_0` is a PE stub, so it's listed as a thunk) and the `0x1400014AB in helper` call site (`check_stdout_line()`), the summary `[+] Marked 22 new call locations` (10 without the fallbacks), 22 bookmarks and comments, and comments matching bookmarks. The UCRT prefix isn't exercised here (mingw doesn't use it); the unit tests cover it.
6. `test_glibc_aliases()`: regression test for glibc aliases. Runs the real binary against `tests/data/static_glibc`, a statically linked, not stripped ARM64 ELF without source (645 KB, the largest test binary), in which IDA names `system` as `__libc_system`. Checks success, the `[BAD 0] system` header and the `0x4007CC in main` call site (`check_stdout_line()`), that the false call site `0x40CA00 in __malloc_arena_thread_freeres` (a `bl __libc_assert_fail` falling through into `realloc`) isn't listed (`check_no_stdout_line()`, pinning `XRefQuery::FAR`), the summary `[+] Marked 756 new call locations` (742 without the glibc prefixes, 760 with them but with fall-throughs), that `__libc_system` exists in the IDB (`check_function_exists()`, so the scenario fails loudly instead of passing vacuously if a future IDA names the function `system`), 756 bookmarks and comments, and comments matching bookmarks. Most of its marks are calls inside glibc itself, since the binary is static.
7. `test_apple_variant_suffixes()`: regression test for Apple's variant suffixes. Runs the real binary against `tests/data/darwin_variants`, an x86-64 Mach-O built from `tests/data/darwin_variants.c` (`cc -arch x86_64 -O0 -o darwin_variants darwin_variants.c`, 8.7 KB; x86-64 because only x86-64 binaries use `$INODE64`), whose stubs IDA names `_realpath$DARWIN_EXTSN`, `_syslog$DARWIN_EXTSN`, and `_stat$INODE64`, with `popen` unsuffixed as a control. Checks success, the `[BAD 2] stat (thunk)` header and its `0x1000004DE in _main` call site, and the `[BAD 2] realpath (thunk)` header (`check_stdout_line()`, one per suffix kind, so that losing either fails even if the count stays the same), the summary `[+] Marked 4 new call locations` (1 without the suffixes stripped, only `popen`), that `_stat$INODE64` and `_realpath$DARWIN_EXTSN` exist and are thunks (`check_thunk_exists()`, so the scenario fails loudly instead of passing vacuously if a future IDA names the stubs differently), 4 bookmarks and comments, and comments matching bookmarks.
8. `test_x86_argument_size()`: regression test for the size of the arguments in 32-bit x86 names. Runs the real binary against `tests/data/stdcall_stubs`, an i686 PE built with mingw from `tests/data/stdcall_stubs.c` (build command in the source, 38 KB; renamed without `.exe`, like `import_stubs`) and stripped of debug info only, so that IDA names the stubs after their symbols, `_WinExec@8`, `_lstrcpyA@8`, and `_LoadLibraryA@4` (a fully stripped build names them `WinExec` etc., so it wouldn't test anything). The source declares the three functions itself, without `dllimport`, since `<windows.h>`'s declarations would make the calls go through the import address table instead of the stubs. Checks success, the `[BAD 1] WinExec (thunk)` header and its `0x4014EE in _main` call site, and the `[BAD 0] lstrcpyA (thunk)` header (`check_stdout_line()`), the summary `[+] Marked 19 new call locations` (16 without the argument size stripped), that `_WinExec@8` and `_lstrcpyA@8` exist and are thunks (`check_thunk_exists()`), 19 bookmarks and comments, and comments matching bookmarks.
9. `test_user_bookmark_at_call_site()`: regression test for overlaid bookmarks. Creates the IDB of `tests/data/double_xref` with `IDB::open_with(.., true, true)` (so it's saved) and a user bookmark (`USER_BOOKMARK_DESC`) at the call site `USER_BOOKMARK_ADDR` (`0x7F4`), then runs rhabdomancer twice: the first run must mark exactly 1 location (before the fix it marked 2, because the call site is reached through both `system (thunk)` and `system` and each lookup by address returned the user's bookmark), the second must mark 0, and the IDB must hold 2 bookmarks with the user's unchanged. It doesn't run `check_comments_match_bookmarks()`, since the user's bookmark has no matching comment.
10. `test_user_comment_at_call_site()`: regression test for the comment check. Creates the IDB of `tests/data/double_xref` with a user comment (`USER_COMMENT`, via `add_user_comment()`) at the call site `USER_COMMENT_ADDR` (`0x7F4`), runs rhabdomancer twice (1 mark, then 0), and checks 1 bookmark, 1 comment, and that the comment is exactly `USER_COMMENT_MARKED` (`"user comment\n[BAD 0] system"`: the tag is added after the user's text, separated by a newline, as IDA's `append_cmt` would). This pins the `contains(PREFIX)` comment check: with `starts_with`, the tag was appended on every visit (4 times over the two runs). It doesn't run `check_comments_match_bookmarks()`, since the comment doesn't start with the tag.
11. `test_user_comment_at_comment_limit()`: regression test for user comments too long for the tag. Runs twice, each time from a fresh IDB of `tests/data/double_xref` with a user comment of `y`s at `USER_COMMENT_ADDR` (`0x7F4`, via `add_user_comment()`, which takes the comment's text): 1009 bytes, which with the newline and the 14-byte `[BAD 0] system` gives exactly IDA's 1024 bytes, and 1010 bytes, one more. Each time it runs rhabdomancer twice (1 mark, then 0) and checks 1 bookmark and the exact comment (`check_user_comment()`): the 1009-byte comment followed by `\n[BAD 0] system`, and the 1010-byte one unchanged. This pins `MAX_COMMENT_LEN` against what IDA really stores: with 1025, the second comment ended in a cut-off tag, and with 1023, the first got no tag. The warning on stderr isn't checked, since the in-process run doesn't capture it.
12. `test_call_site_at_function_start()`: regression test for call locations at a function's start. Runs rhabdomancer twice (2 marks, then 0) against `tests/data/tail_call`, an arm64 Mach-O built from `tests/data/tail_call.c` (`cc -arch arm64 -O2 -o tail_call tail_call.c`, 33 KB) whose wrapper `_xfree` is only `b _free`, so its call location `TAIL_CALL_ADDR` (`0x100000410`) is the wrapper's start. Checks that the address is a function's start (`check_function_start()`, so the scenario fails loudly instead of passing vacuously if a future IDA delimits the function differently), 2 bookmarks and comments, comments matching bookmarks, and that the instruction comment there is exactly `TAIL_CALL_COMMENT` (`[BAD 2] free`) and the function has no comment (`check_function_start_comment()`). With `append_cmt`, the instruction had no comment and the function comment read `[BAD 2] free\n[BAD 2] free` after the two runs.
13. `test_empty_configuration_variable()`: runs the real binary against `tests/data/no_calls` with `RHABDOMANCER_CONFIG` set to an empty value and checks with `check_binary_succeeded()` that it succeeds, i.e., uses the built-in configuration instead of failing to read an empty path. It checks the exit status, not the `Using built-in configuration` line, so rewording that line doesn't break the test. A subprocess is needed because the in-process harness removes the variable (see below).
14. `test_invalid_configuration()`: runs with `INVALID_CONFIG_TOML` (the same function under two priorities once normalized) and checks that `run()` fails with the duplicate error and that no IDB file is created, since the configuration is loaded before the binary is opened.
15. `test_missing_configuration()`: points `RHABDOMANCER_CONFIG` at a configuration file that doesn't exist (`config_path(MISSING_CONFIG)`, removed first if present) and checks that `run()` fails with an `io::Error` of kind `NotFound` somewhere in its error chain (found by downcasting each cause; deliberately not a message: the OS's wording varies by platform, and rhabdomancer's own context message can be reworded without breaking the test) and that no IDB file is created.
16. `test_missing_binary()`: runs against the nonexistent `tests/data/missing` and checks that `run()` fails with `failed to analyze binary file` and creates no IDB file.
17. `test_invalid_arguments()`: runs the real binary (via `run_binary()`) with no arguments, two arguments, `-h`, and `--help`, and checks with `check_usage()` that each run fails, prints `Usage:` to stderr and nothing to stdout, and creates no IDB file for `tests/data/no_calls` (the two-argument case passes it twice). Covers the only branching in `src/main.rs`; IDA never opens a database here, so it's fast.
- `BAD_PREFIX` is deliberately the literal `"[BAD "` (`PREFIX` is private anyway): the annotation text is an external contract (users and scripts search IDBs for it), so an accidental change to the tags rhabdomancer writes must fail the tests. The same applies to other expected values (`CUSTOM_MEDIUM`, the `[BAD 1] ` tag, error substrings): keep them as literals.
- `main()` removes `RHABDOMANCER_CONFIG` before running any scenario, so a value exported in the developer's shell can't replace the built-in configuration that the in-process scenarios expect (all but 2, 14, and 15, which set their own) (`run_binary()` also removes it from the subprocess's environment).
- Helpers: `reset_idb()` removes all IDB files of a binary, packed (`.i64`) or unpacked (`IDB_EXTENSIONS`), if present (every scenario starts and ends with it, so a crashed run doesn't poison the next); `open_idb()` opens an IDB and enables hidden comments/functions/instructions/segments before checks; `config_path()` returns a configuration file path under `env::temp_dir()` (named by label and process ID, never inside the source tree); `run_with_config_path()` sets `RHABDOMANCER_CONFIG` to a path for one run, then unsets it; `run_with_config()` writes a configuration file at `config_path(label)`, runs via `run_with_config_path()`, then removes the file, returning the run's result (nested in the outer `anyhow::Result` for file I/O errors) so that callers can check expected errors. `run_binary(args, config)` runs the real binary with `args` and `RHABDOMANCER_CONFIG` set to `config` or removed (`None`), forwards its stderr, and returns its `process::Output`, without checking its status: scenarios expecting success call `check_binary_succeeded()` (same names and pattern as augur and haruspex), and the stdout checks (`check_listing()`, `check_priority_order()`) take the `Output`. Scenarios `drop()` their IDB before rhabdomancer reopens the database.

Conventions shared by the augur, haruspex, and rhabdomancer harnesses:

- All scenarios run sequentially in the same process; the harness stops at the first failed check, and its progress messages go to stderr.
- Expected values that pin an external contract (CLI output lines, summaries, file names, annotation tags, error substrings) are literals, never production constants, so that an accidental change fails the tests.
- Expected errors are matched against the full error chain (`format!("{err:#}")`), i.e., what users see; OS-dependent failures are checked by downcasting to `io::ErrorKind`, not by message.
- Only the module-level `#![expect(clippy::panic_in_result_fn)]` is needed: fallible lookups use `.context(...)?` instead of `expect`, and conversions use `try_from` instead of `as`.
- New checks must be shown to fail: temporarily break the behavior they guard, run the suite, restore. If an earlier check catches the break first, break it differently, so that the new check is shown to fail on its own.

## IDA integration notes

- `IDB::open_with(path, true, true)` opens or creates an `.i64` IDB file with auto-analysis enabled and the database kept after closing.
- `idalib::force_batch_mode()` must be called before opening any database (suppresses IDA UI); `main()` and the test harness both call it first.
- IDA must run on the main thread and isn't thread-safe, so standard `#[test]` functions, which run on worker threads, can't use it: that's why the integration tests use a custom harness (`harness = false`).
- Objects derived from an `IDB` (e.g., `Function`, `CFunction`) must be dropped before the `IDB` itself, since their destructors call into IDA, and getting it wrong hangs the process. Since idalib 0.11, `Function`, `Segment`, and `CFunction` implement `Drop`, so the borrow checker enforces this: dropping the `IDB` while one of them is still alive fails to compile (E0505 for an explicit `drop(idb)`, E0597 when the `IDB` goes out of scope first).
- Names from the analyzed binary (function names, strings) are untrusted: print them escaped with `str::escape_debug()` (or `{:?}`) at the print site, and build file names from them only through a sanitizer.
- To probe IDA's view of a binary, write a temporary `examples/` program (`cargo run --example ...`), then delete it.
- Annotation is idempotent — existing bookmarks/comments are not duplicated, even when a user's own bookmark shares the address (see `CallMarker`).
- `.plt` sections in ELF binaries require following thunk indirection to reach the real import's callers; `traverse_xrefs` handles this.
- Direct IAT calls aren't handled: with `__declspec(dllimport)` (MSVC declares the Win32 API this way, and the CRT too in `/MD` builds), the compiler calls through the import address table (`call [__imp_X]` on x64; `adrp`/`ldr`/`blr` on ARM64) instead of through a `jmp [__imp_X]` stub. IDA treats the `__imp_X` slot as data, not a function, so `find_all()` never matches it, and the call site only has a data XREF to the slot, which `traverse_xrefs()` skips anyway. Such calls are silently missed. This was reproduced on mingw builds with `dllimport` added by hand. None of the binaries checked so far has such calls (`cmd.exe` calls every import through a stub), so how much is missed on a real MSVC x64 `/MD` release build hasn't been measured yet, and that measurement should come before any design. A fix would match the `__imp_X` names (with the prefix removed) through `lookup()`, and walk the data XREFs to the slot that come from code (on ARM64, from the `ldr`). It would also skip XREFs from stubs, whose own `jmp [__imp_X]` references the slot too; that's the rule for which referencing functions are stubs that the `strip_ida_suffix()` entry mentions. It's a README TODO.

## CI workflows

- **`build.yml`** — lint/build/test matrix across Linux, macOS, and Windows, plus a `zizmor` job that audits `.github/workflows/*.yml` for security issues (credential handling, injection, etc.).
- **`doc.yml`** — builds rustdoc and pushes it to the `gh-pages` branch on `v*` tags; its `checkout` step needs persisted git credentials to `git push` later, so it carries a `# zizmor: ignore[artipacked]` suppression comment.
- To suppress a specific zizmor finding, add an inline `# zizmor: ignore[<rule-id>]` comment on the flagged step with a short justification, rather than disabling the rule globally.
