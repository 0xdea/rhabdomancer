# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Project Is

**Rhabdomancer** is a headless IDA 9.x plugin (written in Rust) that locates calls to potentially insecure API functions in binary files. It uses `idalib` — Rust bindings to the IDA SDK — and requires a valid IDA installation to build and run.

## Build Requirements

- IDA 9.x installation with `IDADIR` environment variable set
- LLVM/Clang (required by `idalib` for bindgen)
- Rust (edition 2024)

The `build.rs` script uses `idalib-build` to auto-configure IDA SDK linkage. It emits a warning (but does not fail) if `IDADIR` is unset.

## Commands

```bash
# Build
cargo build --release --locked     # optimized (LTO, stripped, O3)
cargo build --locked               # debug build

# Unit tests (standard test framework, no IDA database needed)
cargo test --lib --locked

# Integration tests (use a custom harness, not the standard Rust test framework)
cargo test --test tests --locked

# Lint & format (CI enforces these as errors)
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings

# Documentation (CI enforces this as an error via RUSTDOCFLAGS=-D warnings)
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps --locked

# Dependency vulnerability audit (CI enforces this; requires cargo-audit)
cargo audit
```

`--workspace` follows the `rust-style` skill; rhabdomancer is a single crate, so it is equivalent to CI's `cargo clippy --all-targets --locked -- -D warnings`. `--no-deps` matches CI's `build.yml` doc step and skips documenting dependencies (`doc.yml`, which publishes to `gh-pages`, runs a plain `cargo doc --locked`).

CI's own `test` step only runs `cargo test --no-run` — a compile-only smoke check. Both test suites link against the IDA libraries, and the integration suite in `tests/main.rs` also needs a working IDA installation to analyze binaries, which CI runners don't have, so both only run locally.

## Architecture

Three source files:

- **`src/main.rs`** — CLI entry point. Parses a single binary path argument, calls `force_batch_mode()` to suppress IDA UI, then delegates to `lib::run()`.
- **`src/lib.rs`** — Core analysis logic. Public entry point: `run(filepath: impl AsRef<Path>) -> anyhow::Result<BookmarkIndex>`. It is the only public item: everything else, including `PREFIX` (`"[BAD "`, private since 1.0), is internal, so the public API stays minimal (making items public later is non-breaking; CI runs `cargo-semver-checks`). A library API for other crates (e.g., a `scan()` returning findings without printing) would be designed separately rather than by exporting these CLI-oriented types. The annotation text `[BAD n] <name>` is still an external contract, documented in the README: users and scripts search IDBs for it, and IDBs annotated by previous versions carry it, so never change it. Key types:
  - `KnownBadFunctionsConfig`: Mirrors the configuration file (`high`/`medium`/`low` name lists); only used as the deserialization source of `KnownBadFunctions`.
  - `KnownBadFunctions`: Loads the configuration into a single `HashMap<String, Priority>` keyed by normalized name. Deserialized via `#[serde(try_from = "KnownBadFunctionsConfig")]`: the `TryFrom` impl normalizes every name and rejects the configuration at the first name that is empty or is listed under multiple priorities (after normalization), so `parse()` deserializes straight into `Self` with `toml::from_str`. `load()` parses the file at `RHABDOMANCER_CONFIG` if set and not empty (an empty value counts as unset, so clearing the variable restores the built-in list) (read with `fs::read_to_string`, adding the file path as `anyhow` context to read and parse errors), or the built-in `DEFAULT_CONFIG` otherwise, printing `[*] Using built-in configuration (set RHABDOMANCER_CONFIG to use a custom one)` so the way to customize is shown on every run (with no fallback to a file on disk, so which configuration is used never depends on the source tree); the unit tests call `parse()` directly, so they exercise the same parsing path as `load()`. Duplicates are detected with `*functions.entry(name).or_insert(priority) != priority`, which keeps the first occurrence and compares against it in one expression. `lookup()` normalizes a `&str` and returns the stored normalized name (via `get_key_value`, borrowed from the map) and its priority, so callers never normalize twice; it is unit-testable without an IDB.
  - `BadFunctions<'a>`: Pure data: the bad functions found in the opened IDB, in a single `BTreeMap<(Priority, FunctionId), (Function<'a>, &'a str)>`, so iteration visits high, then medium, then low priority, each ordered by function ID. In ELF binaries a bad API function usually matches twice, as its `.plt` stub (printed as `(thunk)`) and as its import, and both are kept on purpose, so their call sites are listed twice (on `tests/data/ls` all 10 functions appear as identical thunk/import pairs; `tests/data/double_xref` pins it for `system`). Don't deduplicate them: dropping the stub by name would lose its marks whenever the import's traversal doesn't reach its callers (an unrelated function that normalizes to the same name, e.g. a local `_strlen` vs `strlen@plt`, or a stub IDA doesn't link to the import). A structural check (drop the stub only if the import has an XREF from inside it) would be safe, but was rejected in favor of simplicity: the repetition is cosmetic, since the `bookmarked` set marks each call site once. `find_all()` is a single `filter_map(...).collect()` that fetches each function's name once (an FFI call plus a `String` allocation) and stores the function with the normalized name returned by `lookup()`, borrowed from `KnownBadFunctions` (hence `find_all(idb: &'a IDB, bad: &'a KnownBadFunctions)`, a single lifetime for both borrows). `iter()` exposes the entries as flat `(priority, id, func, name)` tuples in map order, so consumers such as `CallMarker` don't depend on the map's layout; it has no `#[must_use]` because `impl Iterator` already is (adding one triggers clippy's `double_must_use`).
  - `CallMarker<'a>`: Annotates an IDB, holding the context that marking needs: the `&'a IDB` itself, its `PltSegments`, and `bookmarked`, the set of addresses that already carry one of rhabdomancer's bookmarks (see below), so none of them is passed around as a parameter. `mark_all(&found)` iterates `found.iter()` (ignoring the function ID) and totals the counts returned by `mark_calls()` with `.sum()` over `Result<BookmarkIndex, IDAError>`, which stops at the first error; `run()` adds the `anyhow` context. `mark_calls()` receives each function's priority and name, formats the description (`[BAD n] <normalized name>`) itself, and returns the count from `traverse_xrefs()` (`0` for a function without XREFs); `traverse_xrefs()` counts newly added bookmarks with `saturating_add`. Keep IDB-dependent marking state (e.g., a visited set for thunk cycles) here rather than in `BadFunctions`. Idempotency: `CallMarker::new()` builds `bookmarked` from every bookmark index (`get_address(idx)` + `get_description_by_index(idx)` containing `PREFIX`), and `traverse_xrefs()` marks an address only if `self.bookmarked.insert(from)` succeeds, which also records the bookmarks added during the run, so a call site reached through several bad functions is bookmarked once. Never look a bookmark up by address (`get_description(ea)`): IDA overlays bookmarks added at an already bookmarked address, and a lookup by address returns only one of them, which may be a user's own; that made rhabdomancer re-mark such call sites on every run and even twice within one (pinned by `test_user_bookmark_at_call_site()`). The marking methods take `&mut self` because the set is updated during the walk. Comments don't need this: the `get_cmt(from)` check sees the whole comment text. Both checks deliberately use `contains(PREFIX)`, not `starts_with`: for comments it's required, because `append_cmt` adds the tag after any existing comment; for bookmarks it keeps one of rhabdomancer's bookmarks that a user edited by prepending text recognized (so it isn't marked again), at the cost of a user's own bookmark that merely mentions the prefix counting as rhabdomancer's. Every version has written descriptions starting with `[BAD `, so either check recognizes older IDBs.
  - `Priority` enum: `High`/`Medium`/`Low` — maps to BAD 0/1/2. Variants are declared from highest to lowest priority, and the derived `Ord` follows declaration order (no explicit discriminants or `#[repr]`), which is what orders `BadFunctions`' map: keep this order when editing the enum. `level()` maps each variant to its tag digit with an explicit `match` (deliberately not a cast, so tags don't depend on declaration order), and `description()` builds `[BAD n] <name>` as `format!("{PREFIX}{}] {func_name}", self.level())`, so tags are derived from the `PREFIX` constant and can't drift from it. The `description_formats_tag_and_name` unit test pins the full format with literals.
  - `CallMarker::traverse_xrefs(target, desc)`: Iteratively walks the XREFs to `target` with a worklist of addresses: each popped address's chain is walked with `for xref in iter::successors(first_xref_to(addr, ...), XRef::next_to)` (an address without XREFs yields nothing, so `mark_calls()` just passes `func.start_address()`). Handles `.plt` thunk indirection for ELF binaries: when an XREF comes from a `.plt` segment, the containing thunk's start address (`function_at(from).map(|func| func.start_address())`, no `BADADDR` sentinel) is queued and its XREFs walked after the current chain; the explicit worklist keeps deep indirection from overflowing the call stack. A `visited` set, seeded with `target`, makes each address queued at most once. That fixes a real bug: when a `.plt` stub references the import more than once, as IDA sees AArch64 stubs (`tests/data/double_xref`), the stub's XREFs were walked once per reference, listing its callers twice (pinned by `test_thunk_with_repeated_xrefs()`). It also makes cyclic `.plt` references terminate. Such cycles don't occur in compiler-generated binaries as IDA analyzes them (on `tests/data/ls`, IDA splits every lazy-binding `.plt` stub into its own function, and nothing the walk visits is referenced from them; the 47 `jmp PLT0` XREFs form no cycle), but they can in crafted binaries or if IDA delimits `.plt` functions differently (e.g., one function spanning PLT0 and the stubs would reference itself), and rhabdomancer runs on untrusted input. The integration tests can't exercise the cycle case; it was checked by forcing a self-cycle (terminates with the guard, hangs without it). Call-site order is not a contract: a chain's direct callers are listed before the callers reached through its thunks (on `tests/data/ls` imports have no direct callers, so the output matches the earlier recursion-like order). Early `continue`s (for `.plt` and non-code XREFs) avoid an `if`/`else if` without `else`. `self.idb.bookmarks()` (a zero-cost `PhantomData` wrapper) is bound once per traversal.
  - `PltSegments`: The address ranges of all `.plt*` segments of the IDB, collected once by `PltSegments::new()` (no per-call FFI lookups). `contains()` checks whether an address falls within any of them; the ranges are half-open `Range<Address>` values, matching IDA's `range_t` (`end_ea` excluded), which unit tests pin without an IDB.
  - `normalize_name()`: Strips leading dots/underscores from function names for cross-platform matching.
  - Output convention: scan results (bad-function headers and call-site locations) print to stdout via `println!`; everything else (banners, progress, summary/timing, errors) prints to stderr via `eprintln!`. Preserve this split when adding new output.
- **Unit tests** — `#[cfg(test)] mod tests` at the end of `src/lib.rs` covers the logic that doesn't need an IDB: priority mapping, normalization of both configuration and function names, merging of duplicates within the same priority, rejection of names that normalize to empty (and no match for function names that do), rejection of names listed under multiple priorities (via `TryFrom` and via `parse()`, checking the error message), validity of the built-in configuration (`DEFAULT_CONFIG`, the same constant the binary uses, so a duplicate in `conf/rhabdomancer.toml` fails the unit tests), `Priority::description()`'s exact `[BAD n] <name>` format, `PltSegments::contains()` (start included, end excluded, every range checked, empty ranges match nothing; test values are built from `(start, end)` pairs via a `plt()` helper, because clippy's `single_range_in_vec_init` rejects `vec![start..end]`), and the `Priority` order `High < Medium < Low` (which determines processing order, so reordering the variants fails a test).
- **`tests/main.rs`** — Custom-harness integration tests, structured like augur's: documented constants at the top, a `main()` that calls `idalib::force_batch_mode()` and then one `test_*` function per scenario, and one `check_*` function per assertion (each printing its own `[*] Checking ... Ok.` line). Scenarios:
  1. `test_default_configuration()` (against `tests/data/ls`): asserts exactly 86 marked locations, then checks bookmark count, that every bookmark description starts with `BAD_PREFIX`, comment count, and that the comment at every bookmarked address starts with that bookmark's description. It then runs again on the same IDB and asserts 0 new marks (idempotency lives here because it depends on this scenario's IDB).
  2. `test_custom_configuration()`: runs with `CUSTOM_CONFIG_TOML` via `RHABDOMANCER_CONFIG`, asserts exactly 13 marks, and runs the same bookmark count, comment count, and comment-matches-bookmark checks as scenario 1, plus an exact check that every bookmark description is `[BAD 1] ` followed by one of the normalized names in `CUSTOM_MEDIUM`. Since the custom config includes decorated names (`_fwrite`, `.memset`), this verifies that both bookmarks and comments use normalized names.
  3. `test_invalid_configuration()`: runs with `INVALID_CONFIG_TOML` (the same function under two priorities once normalized) and checks that `run()` fails with the duplicate error and that no IDB file is created, since the configuration is loaded before the binary is opened.
  4. `test_missing_configuration()`: points `RHABDOMANCER_CONFIG` at a configuration file that doesn't exist (`config_path(MISSING_CONFIG)`, removed first if present) and checks that `run()` fails with an `io::Error` of kind `NotFound` somewhere in its error chain (found by downcasting each cause; deliberately not a message: the OS's wording varies by platform, and rhabdomancer's own context message can be reworded without breaking the test) and that no IDB file is created.
  5. `test_binary_without_calls()`: runs against `tests/data/no_calls`, a minimal macOS arm64 Mach-O binary built from `tests/data/no_calls.c` (`cc -O0 -o no_calls no_calls.c`, the same binary as augur's `no_strings`), and asserts 0 marks, 0 bookmarks, and 0 comments.
  6. `test_thunk_with_repeated_xrefs()`: regression test for duplicated call-site lines. Runs the real `rhabdomancer` binary (`env!("CARGO_BIN_EXE_rhabdomancer")`, via `run_binary()`, with `RHABDOMANCER_CONFIG` removed) against `tests/data/double_xref`, an ARM64 ELF whose `main` calls `system` through `system@plt`, and pins its exact stdout (`DOUBLE_XREF_LISTING`): IDA sees the AArch64 stub (`adrp`/`ldr`/`add`/`br`) referencing the `system` import more than once, so without `traverse_xrefs()`' visited set the stub's XREFs were walked once per reference and `0x7F4 in main` was listed twice. The bookmark check already deduplicated the marks, so only the stdout listing shows the bug, which is why this scenario captures stdout through a subprocess (`rhabdomancer::run()` prints it directly). It also checks 1 bookmark, 1 comment, and comments matching bookmarks. The listing shows `system` twice (thunk and import), which is deliberate (see `BadFunctions`).
  7. `test_priority_order()`: runs the real binary (via `run_binary()`) against `tests/data/ls` and checks with `check_priority_order()` that the levels of the `[BAD n]` headers in stdout never decrease (high, then medium, then low), and that more than one level appears (on `ls`: medium, then low), so the check isn't vacuous. The `Priority` unit test pins only the enum's order; this pins that the output follows it (reversing `BadFunctions::iter()` fails it).
  8. `test_user_bookmark_at_call_site()`: regression test for overlaid bookmarks. Creates the IDB of `tests/data/double_xref` with `IDB::open_with(.., true, true)` (so it's saved) and a user bookmark (`USER_BOOKMARK_DESC`) at the call site `USER_BOOKMARK_ADDR` (`0x7F4`), then runs rhabdomancer twice: the first run must mark exactly 1 location (before the fix it marked 2, because the call site is reached through both `system (thunk)` and `system` and each lookup by address returned the user's bookmark), the second must mark 0, and the IDB must hold 2 bookmarks with the user's unchanged. It doesn't run `check_comments_match_bookmarks()`, since the user's bookmark has no matching comment.
  9. `test_user_comment_at_call_site()`: regression test for the comment check. Creates the IDB of `tests/data/double_xref` with a user comment (`USER_COMMENT`, via `add_user_comment()`) at the call site `USER_COMMENT_ADDR` (`0x7F4`), runs rhabdomancer twice (1 mark, then 0), and checks 1 bookmark, 1 comment, and that the comment is exactly `USER_COMMENT_MARKED` (`"user comment\n[BAD 0] system"`: `append_cmt` adds the tag after the user's text, separated by a newline). This pins the `contains(PREFIX)` comment check: with `starts_with`, the tag was appended on every visit (4 times over the two runs). It doesn't run `check_comments_match_bookmarks()`, since the comment doesn't start with the tag.
  10. `test_missing_binary()`: runs against the nonexistent `tests/data/missing` and checks that `run()` fails with `failed to analyze binary file` and creates no IDB file.
  - `BAD_PREFIX` is deliberately the literal `"[BAD "` (`PREFIX` is private anyway): the annotation text is an external contract (users and scripts search IDBs for it), so an accidental change to the tags rhabdomancer writes must fail the tests. The same applies to other expected values (`CUSTOM_MEDIUM`, the `[BAD 1] ` tag, error substrings): keep them as literals.
  - `main()` removes `RHABDOMANCER_CONFIG` before running any scenario, so a value exported in the developer's shell can't replace the built-in configuration that the in-process scenarios expect (all but 2–4, which set their own) (`run_binary()` also removes it from the subprocess's environment).
  - Helpers: `reset_idb()` removes all IDB files of a binary, packed (`.i64`) or unpacked (`IDB_EXTENSIONS`), if present (every scenario starts and ends with it, so a crashed run doesn't poison the next); `open_idb()` opens an IDB and enables hidden comments/functions/instructions/segments before checks; `config_path()` returns a configuration file path under `env::temp_dir()` (named by label and process ID, never inside the source tree); `run_with_config_path()` sets `RHABDOMANCER_CONFIG` to a path for one run, then unsets it; `run_with_config()` writes a configuration file at `config_path(label)`, runs via `run_with_config_path()`, then removes the file, returning the run's result (nested in the outer `anyhow::Result` for file I/O errors) so that callers can check expected errors. Error checks match against `{err:#}` (the full context chain). Scenarios `drop()` their IDB before rhabdomancer reopens the database.
  - Only the module-level `#![expect(clippy::panic_in_result_fn)]` is needed: fallible lookups use `.context(...)?` instead of `expect`, and conversions use `usize::try_from` instead of `as`.
  - New checks must be shown to fail: temporarily break the behavior they guard, run the suite, restore.

## Configuration

All "bad" functions are defined in `conf/rhabdomancer.toml`, grouped into `high`, `medium`, and `low` arrays. The file is embedded in the binary at build time as `DEFAULT_CONFIG` (`include_str!`), replacing the earlier path built from `CARGO_MANIFEST_DIR`, which broke binaries whose source tree was moved or deleted (e.g., after `cargo install`); editing it requires a rebuild. A custom configuration file can be used instead by setting the `RHABDOMANCER_CONFIG` environment variable to its path. `conf/` must stay in the published package (not in `Cargo.toml`'s `exclude`), since `include_str!` needs it when building from crates.io. The loader reads the file with `fs::read_to_string` and deserializes it with the `toml` crate (`toml::from_str`, features `std`, `serde`, and `parse` only) via serde; the parse error type is imported as `TomlError`. Each name may appear under only one priority (leading dots/underscores are ignored when comparing names); otherwise loading fails with an error naming the (normalized) duplicate. Repeats within the same priority are harmless and merged. Entries that are empty once normalized (e.g. `""`, `"_"`, `"."`) are also rejected, with an error showing the original spelling.

## Lint Policy

The workspace `Cargo.toml` enables aggressive lints. Notably forbidden everywhere except tests:

- `unwrap`, `expect`, `panic`, `todo`, `unimplemented`, `unreachable`, `dbg_macro`
- Unsafe blocks require a `reason` attribute

`clippy::min_ident_chars` is enabled, so single-character identifiers (e.g. `|s|`, `for f in`) are flagged — use descriptive names like `name`, `func`, `idx`. Clippy's default `allowed-idents-below-min-chars` still permits `i`, `j`, `x`, `y`, `z`, `w`, and `n`, and parameters that keep a trait's own name (such as `f` in `fmt::Display::fmt`) are not flagged either; prefer descriptive names (e.g. `idx`) anyway.

Pure functions whose result matters carry `#[must_use]`, private ones included (clippy's `must_use_candidate` only flags public items): currently `Priority::level()`, `Priority::description()`, `KnownBadFunctions::lookup()`, `PltSegments::contains()`, and `normalize_name()`.

Use `#[expect(clippy::some_lint, reason = "...")]` to locally suppress a specific lint anywhere it genuinely cannot be avoided — in both library code and tests. The only one left in the codebase: `panic_in_result_fn` (test assertions, as a module-level `#![expect]` in `tests/main.rs` and on `mod tests` in `src/lib.rs`). `env::set_var`/`remove_var` are `unsafe` in Rust edition 2024; wrap them in `unsafe {}` with a `// Safety:` comment explaining the single-threaded context, as `run_with_config()` in `tests/main.rs` does.

## IDA Integration Notes

- `IDB::open_with(path, true, true)` opens or creates an `.i64` IDB file with auto-analysis enabled and the database kept after closing.
- `idalib::force_batch_mode()` must be called before opening any database (suppresses IDA UI).
- Annotation is idempotent — existing bookmarks/comments are not duplicated, even when a user's own bookmark shares the address (see `CallMarker`).
- `.plt` sections in ELF binaries require following one level of thunk indirection to reach the real import; `traverse_xrefs` handles this.

## CI Workflows

- **`build.yml`** — lint/build/test matrix across Linux, macOS, and Windows, plus a `zizmor` job that audits `.github/workflows/*.yml` for security issues (credential handling, injection, etc.).
- **`doc.yml`** — builds rustdoc and pushes it to the `gh-pages` branch on `v*` tags; its `checkout` step needs persisted git credentials to `git push` later, so it carries a `# zizmor: ignore[artipacked]` suppression comment.
- To suppress a specific zizmor finding, add an inline `# zizmor: ignore[<rule-id>]` comment on the flagged step with a short justification, rather than disabling the rule globally.
